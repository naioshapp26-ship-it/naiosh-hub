تاريخ المراجعة: 2026-10-13  
الفرع المدموج: `cursor/subscription-packages-points-ee32` → `main` (PR #234)  
متابعة صلابة الحفظ/البوابات: `cursor/packages-ops-harderning-ee32`

## معيار FULL PASS (لم يتحقق بعد)

شراء نقاط مدفوعة → تأكيد بوابة → إضافة للمحفظة → خصم عند خدمة → ظهور السجل للعميل والإدارة من طرف لطرف على الإنتاج.

**لا FULL PASS في هذا التقرير.**

## 1) ما يعمل فعليًا على الإنتاج (مُختبر عبر API بعد الدمج)

| القدرة | النتيجة على الإنتاج |
|---|---|
| صفحة `/packages.html` | تعمل |
| كتالوج الباقات 300 / 6000@$15 / 16000@$35 | يعمل |
| FX حي (USD→SAR/EGP…) + كاش | يعمل (مزود open.er-api / exchangerate-api) |
| فصل عملة العرض عن عملة التحصيل | يعمل (مثال: عرض EGP / تحصيل USD) |
| منح 300 مجانًا مرة واحدة + رفض التكرار 409 | يعمل على حساب اختبار إنتاجي |
| محفظة العميل `/api/client/wallet` تعرض الرصيد والسجل بعد المنح | يعمل |
| Stripe بدون مفاتيح → 503 «الدفع غير متاح» بدون إضافة نقاط | يعمل |
| طلب مراجعة إدارية للباقة المدفوعة بدون إضافة نقاط | يعمل |
| إدارة `/api/admin/packages/*` بدون جلسة موظفين → 401 | يعمل (مقفلة) |

حساب اختبار إنتاجي (مثال): منح مجاني `PKG-…` → `free=300`، ثم `checkout stripe` = 503، و`manual_review` يبقى `paid=0`.

## 2) ما تم اختباره محليًا فقط / جزئيًا

| القدرة | الحالة |
|---|---|
| E2E `scripts/e2e-subscription-packages.js` | PASS محليًا |
| واجهة الإدارة `#packages-points` في لوحة التحكم | موجودة بالكود؛ لم يُثبت مسار موظف إنتاجي كامل (تأكيد طلب + تدقيق) في هذا التقرير بدون استخدام حساب staff إنتاجي |
| خصم نقاط عند شراء خدمة من مركز العميل (`payWithWallet`) | موجود في المسار التشغيلي؛ لم يُثبت E2E إنتاجي كامل «شراء باقة مدفوعة → استخدام خدمة → خصم» لأن الدفع الإلكتروني غير مفعّل |
| جداول Postgres `hub_package_orders` / audit | مضافة في schema؛ صلابة الـ upsert تُعزَّز في متابعة hardening |

## 3) ما يحتاج تفعيلًا خارجيًا (بدون إرسال مفاتيح في المحادثة)

### توصية البوابات (حسب الدول — لا تعتمد Stripe وحده)

| بوابة | أين تناسب غالبًا | ملاحظات رسوم تقريبية* | المطلوب منك بأمان |
|---|---|---|---|
| **Paymob** | مصر / الإمارات / السعودية / عُمان | مصر SME ≈ 2.75% + 3 ج.م؛ الخليج يختلف حسب العقد | تسجيل تاجر على Paymob في دولة الشركة، تفعيل Integration + HMAC، وضع المفاتيح في **Railway Variables** فقط |
| **Tap Payments** | الخليج + مصر/الأردن (تحقق الأهلية) | شائع ≈ 2.75% + ثابت | حساب تاجر Tap، مفتاح سري + webhook secret في Railway |
| **Moyasar** | السعودية (مدى) | مدى عادة أقل من البطاقات الدولية | حساب Moyasar + مفاتيح في Railway |
| **Stripe** | أفضل إن كان الكيان في دولة مدعومة (مثل الإمارات) | ≈ 2.9% + ثابت | حساب Stripe + Checkout + Webhook إلى `/api/hub/packages/stripe/webhook` عبر Variables |

\*الرسوم تتغير تجاريًا — راجع عقد التاجر الحالي قبل الاعتماد.

**مهم:** عرض السعر بـ EGP/SAR للعرض فقط. عملة التحصيل = ما تدعمه البوابة المفعّلة فعليًا في البيئة.

### ما تفعله أنت بأمان (بدون لصق أسرار هنا)

1. اختر بوابة حسب **دولة تسجيل الشركة** والجمهور (مصر/سعودية/خليج).  
2. أكمل KYC/مستندات التاجر عند البوابة.  
3. أنشئ مفاتيح **Test** أولًا، ثم Live.  
4. أضفها في Railway → Variables (ليس في Git وليس في الشات).  
5. اضبط Webhook URL إنتاجي + سر التوقيع.  
6. أبلغ الفريق أن المفاتيح وُضعت (بدون إرسال القيم) لإعادة فحص مسار الدفع الاختباري.

الكود جاهز لمسار Stripe عند وجود المفاتيح؛ Paymob/Tap/Moyasar مُسجَّلة في طبقة `hub-payment-gateways` كحالة/عملات/توصية، وتنفيذ جلسة الدفع لها يحتاج خطوة تكامل لاحقة بعد اختيار التاجر.

## 4) ما لم يُنفذ بعد / فجوات صريحة

1. **تحصيل إلكتروني حي على الإنتاج** — غير مفعّل (لا مفاتيح تاجر حقيقية في Railway).  
2. **تكامل Paymob الكامل في الكود** — مُنفَّذ على فرع `cursor/paymob-packages-checkout-ee32` (إنشاء دفعة + webhook HMAC + credit idempotent + فشل/استرداد + stub محلي). Tap/Moyasar ما زالا سجل جاهزية فقط.  
3. **إثبات FULL E2E إنتاجي:** دفع مدفوع حي → credit → شراء خدمة بالنقاط → خصم → ظهور للإدارة — **لم يتحقق**؛ يوجد إثبات sandbox عبر `scripts/e2e-paymob-packages-sandbox.js` فقط.  
4. **منع إساءة المجانية** ما زال بسيطًا (علم الحساب + تطابق هاتف) وليس نظام هوية احتيالي متقدم.  
5. **لوحة الإدارة على الإنتاج** تحتاج تحققًا بجلسة staff حقيقية بعد تفعيل التاجر.  
6. راجع `docs/paymob-packages-integration.md` لخطوات تفعيل الحساب والمتغيرات.

## 5) سلامة الدمج (PR #234)

- لم يُمسح نظام المحفظة القديم؛ التوسعة فوق `wallet {paid,free,total,ledger}` و`client_portal` durable.  
- شحن الهيرو المحلي الوهمي أُوقف لصالح التوجيه لـ `packages.html` (إيجابي ضد الأرصدة الوهمية).  
- بدون مفاتيح دفع لا يمكن إضافة نقاط مدفوعة من الواجهة.  
- متابعة hardening: حفظ أقوى لـ Postgres (`hub_client_accounts.wallet` + `hub_package_orders`) + سجل بوابات متعددة + ربط أسعار الخدمات عند الخصم من المحفظة.

| السؤال | الجواب |
